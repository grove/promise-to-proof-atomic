# P2PA-001: Promise to Proof–Atomic Integration

**Document type:** Implementation specification  
**Specification revision:** 1.0-draft  
**Date:** 22 September 2026  
**Status:** Proposed for approval; neither an implementation nor an acceptance verdict  
**Target release:** Direct delivery, version 1  
**Normative schema companion:** `promise-to-proof-atomic-contracts.schema.json`

## 1. Purpose and success definition

Implement an optional Atomic workflow that executes Promise to Proof’s direct delivery protocol for one software work item. The integration shall turn a source issue or specification into a saved acceptance contract, a recoverable implementation candidate, a separate implementation review, and a requirement-by-requirement proof. It shall route supported corrections, stop at authorization and agreement boundaries, and preserve sufficient records to inspect and safely continue interrupted work.

The integration’s successful outcome is **VERIFIED**. This means that one exact candidate has a complete, current `REVIEWED` report and a complete, current `PROVEN` report for the same exact agreement. It does not mean that a pull request exists, that required CI has passed, that a repository review requirement has been met, or that merging or deployment is authorized.

The workflow shall report **BLOCKED**, **FAILED**, **CANCELLED**, or **BUDGET_EXHAUSTED** when it cannot meet that success definition. It shall never convert an incomplete or invalid result into success to finish the execution graph.

This document uses **MUST**, **MUST NOT**, **SHOULD**, and **MAY** as normative requirement terms. Requirements become binding when this specification is approved. This document does not itself revise Promise to Proof’s canonical acceptance protocol or constitute a saved acceptance contract for implementing the integration.

## 2. Source baseline and compatibility

The design was checked against these immutable source baselines:

| Project | Commit |
|---|---|
| `grove/promise-to-proof` | `0b67afee1050488bf683df433530cce22139295c` |
| `bastani-inc/atomic` | `e4b02ea10f86e2afe9e485db192a53b0356ee163` |

Promise to Proof already defines agreement ownership, report identities, non-mutating proof, separate review, and the distinction between review corrections and proof-gap repairs. Its contract protocol is authoritative for those meanings. [S1–S3]

Atomic’s checked interfaces include `workflow({...})`, `ctx.task`, `ctx.parallel`, `ctx.tool`, `ctx.ui`, `ctx.workflow`, and `ctx.runId`. A task with `schema` supplies structured output through `WorkflowTaskResult.structured`; a schema-backed `stage.prompt()` instead returns the schema value directly. This integration shall use the task interface consistently. [S4–S6]

Atomic checkpoints completed operations but can repeat unfinished operations. Its current implementation can also fall back to a process-local, in-memory backend when durable backend initialization fails. Database health alone is not evidence that a particular execution selected the durable backend. These distinctions are release requirements, not optional operational advice. [S7–S9]

Each released integration package MUST pin and record the tested Atomic build, the integration build, and the exact skill bundle. A run MUST retain the corresponding skill contents, referenced protocol, schemas, workflow definition, and configuration fingerprints. Loading a newer workflow or skill bundle MUST NOT silently reinterpret a retained run. A future Atomic release is compatible only after the conformance tests in section 19 pass against it.

### 2.1 Required Atomic capability addition

The inspected public workflow context does not expose a selected-backend durability flag. The integration therefore has one explicit host prerequisite: expose the following **new, proposed** read-only field on `WorkflowRunContext`:

```ts
readonly persistenceMode: "durable" | "memory";
```

Atomic MUST populate it from the backend actually selected for the execution, using its existing backend `persistent` property, not from a configuration preference or a database connectivity probe. It MUST be available in interactive, headless, fresh, and resumed runs. The authoring declaration and runtime implementation MUST agree. [S6, S9]

The integration MUST refuse to run when this field is absent or is not `"durable"`. It MUST recheck the live value before admitting new work after resumption. This prerequisite may be delivered as a small upstream Atomic change or a tested host build containing that change. Private, version-unchecked deep imports, warning-text matching, and optimistic assumptions are not conforming substitutes. The workflow shall otherwise use the existing public Atomic primitives rather than introduce a second execution engine.

## 3. Release scope

Version 1 MUST deliver the entire direct workflow, including initial acceptance planning, approval and persistence of the agreement, implementation, separate review and proof, review corrections, eligible proof-gap repairs, authorized contract amendments, bounded execution, operator cancellation, and recovery at supported checkpoints.

Version 1 supports one repository and one unsliced work item per run. Sources are a GitHub issue or a local specification file. Work executes on one host with a persistent Atomic backend and a persistent integration artifact directory. Implementation takes place in an integration-owned workspace; it does not overwrite the operator’s source checkout. Approved canonical-contract file writes are the sole exception to the source-checkout non-mutation rule.

The first conforming execution profile is a Docker-compatible Linux container profile, usable from a Linux or macOS host. Atomic’s Node and Bun host distributions MUST both pass the host conformance tests. The workflow code MUST use cross-host Node APIs rather than depend on Bun-only globals. Native Windows execution, distributed workers, and non-container execution profiles are outside the version-1 support claim. [S4]

Version 1 MUST NOT automatically create an originating issue, slice work into child tickets, implement child/parent contract hierarchies, invoke `fix-pr`, commit, push, create a pull request, merge, deploy, or copy the implementation back over the operator’s checkout. It MUST reject parent/child contract inputs with `UNSUPPORTED_PARENT_CONTEXT` rather than ignore their obligations. A source requiring decomposition stops with `DECOMPOSITION_REQUIRED`; it does not start an improvised child workflow.

Automatic slicing and CI repair are follow-on features, not partially implemented version-1 branches. Their future implementation must preserve the extension constraints in section 21.

## 4. Responsibilities and deliverables

The integration consists of a workflow definition, a typed adapter for the skills, deterministic protocol helpers, an artifact/workspace implementation, and an operator-policy adapter.

| Owner | Responsibilities |
|---|---|
| Promise to Proof skills | Interpret the source; author acceptance contracts; implement; review; evaluate evidence; identify supported gaps and amendments. |
| Atomic | Execute stages; maintain workflow checkpoints; display the graph; provide stage lifecycle controls, human-input primitives, and parallel execution. |
| Integration | Validate identities and outputs; save and reread handoffs; enforce transitions; isolate workspaces; bind approvals; coordinate corrections; determine whether reports are current. |
| Operator | Approve the agreement and permitted effects; resolve consequential decisions; supply an authorized execution environment; decide what to do with the verified candidate. |

The integration MUST NOT replace `prove` with Atomic’s generic reviewer, an average score, a reviewer quorum, a successful task return, or green CI. It MUST NOT duplicate the skills’ substantive engineering instructions in a second prompt library. It MAY add role-preserving instructions describing the structured handoff format and runtime-managed paths.

Recommended source layout:

```text
integrations/atomic/
  workflows/promise-to-proof.ts
  lib/contracts.ts       # TypeBox schemas and semantic validators
  lib/controller.ts      # Pure transition reducer
  lib/skill-runner.ts    # Pinned skill invocation and envelope construction
  lib/artifacts.ts       # Immutable artifacts, readback, effect reconciliation
  lib/workspace.ts       # Candidate capture and isolated execution
  lib/policy.ts          # Operator grants and role capabilities
  test/
```

The graph and major branches MUST remain visible in `promise-to-proof.ts`. Support modules MUST be below the top-level discovery directory, not treated as additional workflows. Installation MUST expose a project workflow named `promise-to-proof`, either through an Atomic package or a small `.atomic/workflows/promise-to-proof.ts` entry point. [S4]

A generic `p2p` workflow engine, a separate scheduler, and a second authoritative workflow-state database are non-goals.

## 5. Launch contract

The workflow MUST declare typed Atomic inputs and outputs. Invalid inputs MUST fail before model execution or repository mutation.

| Input | Type / default | Meaning |
|---|---|---|
| `source` | Required string | Exact GitHub issue URL, or `spec:<repository-relative-path>`. Bare issue numbers are not accepted in v1. |
| `review_base` | Required string | Git commit or ref resolved once to a full object ID. This is the comparison base, not the candidate. |
| `execution_profile` | Required string | Operator-owned profile identifying a pinned container image, environment, limits, and permitted tools/services. |
| `contract_location` | Optional string | Existing or approved canonical contract destination. Resolution follows section 7. |
| `artifact_root` | Optional absolute path | Persistent directory outside every source or candidate tree; default is the operator’s state directory under `promise-to-proof/<repository-key>`. |
| `verification_mode` | `parallel` or `sequential`; default `parallel` | Two isolated verification stages, or review followed by proof. Semantics and final gate are identical. |
| `max_corrections` | Integer 0–10; default 3 | Total automatic corrective invocations, including review corrections and proof repairs. Initial implementation is not counted. |
| `max_amendments` | Integer 0–5; default 1 | Authorized contract-amendment cycles after initial contract approval. |
| `authorization_mode` | `interactive` or `preauthorized`; default `interactive` | How exact-subject grants are obtained. |
| `grant_ref` | Required only for `preauthorized` | Reference to an operator-authenticated grant; not a model-generated declaration. |

The invocation repository is resolved from `ctx.cwd`; a missing or ambiguous repository MUST block. `ctx.runId` MUST be present and used as the integration’s execution identity. The source issue repository MUST match the resolved repository identity. Fork or cross-repository source relationships require a later explicit extension.

The launch record MUST include normalized inputs, repository identity, initial commit, fixed comparison base, execution-profile digest, integration/workflow/skill versions, effective correction and amendment limits, Atomic budget settings, and authorization references. Unknown input keys MUST be rejected. Artifact paths MUST be resolved before execution and MUST NOT point inside the candidate through symlinks or parent-directory traversal.

Model selection inherits the operator’s Atomic configuration. Explicit per-stage model overrides MAY be supported through the operator-owned execution profile. The integration MUST record the actual model and available attempt metadata; it MUST NOT claim distinct models or independent model providers merely because it used fresh sessions.

A newly installed workflow is opened using `/workflow promise-to-proof`; Atomic’s input form supplies the typed fields. Status and lifecycle control use the existing `/workflow status <run-id>`, `/workflow pause`, and `/workflow resume <run-id>` surfaces. No new CLI syntax is assumed. [S4, S7]

## 6. Preflight and workspace ownership

Before planning or editing, preflight MUST establish the selected durable backend, retrieve the pinned skill bundle and its references, validate the source, resolve the comparison base, inspect repository state, validate the operator profile, and verify persistent artifact storage with a write/read/delete probe under its own temporary namespace.

Unrelated pre-existing tracked or untracked source changes MUST block with `DIRTY_SOURCE`. An explicitly designated canonical-contract file may differ from Git because its exact contents are captured separately as the agreement. Ignored dependencies are not candidate content by default; the execution profile must identify the environment that supplies them. Ignored source files or fixtures required for behavior must be explicitly included in the capture policy.

The integration MUST acquire exclusive single-host ownership of the work item and its managed workspace before a mutator starts. A second run for the same work item MUST fail admission with `WORK_ITEM_BUSY`. A lock records the run ID, host identity, process identity, and workspace. A time-to-live expiring is not sufficient authority to steal a lock. Reclaim requires proving the previous owner and its owned processes have stopped, or explicit operator reconciliation.

A managed writer workspace MUST be initialized from the captured starting code, not from a mutable branch later in the run. No skill may create an alternative checkout or worktree. Workspace setup belongs to the coordinator and is included in the launch grant. Ordinary implementation changes remain in that workspace and in the final candidate bundle. The final handoff MUST identify its location and include a reviewable patch against the fixed comparison base.

## 7. Canonical agreements and source reconciliation

There MUST be exactly one canonical contract location for the work item. Immutable copies in the artifact store are historical snapshots, not competing canonical agreements. Contract identity is the triple `(canonical location, revision label, SHA-256 of exact UTF-8 bytes)`. Text MUST NOT be normalized, reformatted, or regenerated between hashing, approval, storage, and handoff. A same-revision text change creates a new text identity and invalidates current results. Only an authorized material semantic change increments the revision through `plan-acceptance`. [S1]

For a local specification, the default canonical destination is `docs/acceptance-contracts/<work-id>.md` in the source repository, unless that repository documents another destination. The coordinator may write only this explicitly approved source-checkout path. The work ID is an explicit existing key when available; otherwise it is the lowercase source basename with non-ASCII-alphanumeric runs replaced by hyphens and leading/trailing hyphens removed (or `spec` if empty), followed by a hyphen and the first 12 hexadecimal characters of the normalized source-reference digest.

For a GitHub issue, the adapter MUST reuse its established contract location. In the absence of one, the default is an explicitly authorized contract comment on the originating issue. The adapter MUST NOT create a second issue or replace the issue body. New revisions are appended as immutable, uniquely marked contract records referencing the prior record; the directly discoverable contract index identifies the current accepted revision. Conflicting current records block with `CONTRACT_CONFLICT`. Human edits are never overwritten automatically.

The GitHub-comment implementation uses the logical canonical location `github:<owner>/<repo>#<issue>:acceptance-contract`. Each published contract record has a machine header with `format: p2p-contract/1`, work-item key, operation key, revision, content digest, approval reference, and `supersedes` (the previous comment ID and digest, or null for the first record). The resolver derives the current index from the unique approved terminal record in this supersession chain; there is no separately edited index document. A forked chain, duplicate operation marker, altered approved record, or multiple competing roots blocks. Discovery of an older unmanaged contract requires an explicit migration decision; it MUST NOT silently create a second canonical location. The initial v1 store implementations are local files and managed GitHub issue comments. Other established store types stop `UNSUPPORTED_CONTRACT_STORE` rather than migrate implicitly.

A repository-file contract for a GitHub issue is supported only when the originating issue already links it, or when a narrowly scoped, approved source-link comment is published. A private local pathname alone is not a sufficient GitHub handoff; the reference must resolve through the declared repository/file or an authorized retrievable artifact destination.

`plan-acceptance` MUST return the proposed Markdown contract and a structured requirement index. The adapter MUST derive and validate the index against the Markdown acceptance matrix. Each independently falsifiable material promise has one stable, unique requirement ID. All rows are mandatory for v1 proof; zero-row contracts are invalid. Plan states remain `planned` or `gap` and MUST NOT contain proof verdicts. An evidence-development gap does not, by itself, block implementation when the promised outcome is settled. Unresolved outcome-defining questions do block it.

The exact proposed contract and scoped authority MUST be approved before implementation. Existing valid authority for the same exact subject may be reused. The coordinator MUST save the planner’s bytes verbatim and reread them successfully before issuing the next handoff. Missing storage, failed readback, or an unresolved source discrepancy blocks progression; a chat response is not a saved contract. [S1]

The source snapshot MUST include the issue/specification body, relevant comments and amendments, stable record IDs, retrievable attachments used as requirements, content hashes, and available modification metadata. Adapter-owned contract/audit records are identified explicitly so the adapter’s own successful writes do not masquerade as new source promises. Every other source change stops dependent work for reconciliation; v1 does not ask a hash comparison to decide whether the change is semantic. Comparison uses source body and individual source-record content/modification metadata, not an issue-level timestamp that may change because the coordinator added its own comment. An exclusion applies only to a record ID with a confirmed coordinator receipt and matching bytes, not to any comment that merely copies the machine-marker syntax. Human modification of an adapter-owned contract record is detected through its separate exact-agreement check.

## 8. Candidate and environment identity

A candidate is recoverable content, not just a digest. Version 1 shall use a uniform snapshot representation, even when its content happens to match a Git commit. The record also retains a matching full commit ID when one exists. No commit is required or implicitly authorized. [S1]

A snapshot MUST contain all tracked material, tracked deletions, new non-ignored files, file modes, symlink entries, and explicitly included ignored fixtures relevant to execution. It MUST exclude `.git`, the artifact store, credentials, and declared generated dependency/cache locations. Capturing a symlink records its target without following it; absolute or escaping targets, special files, and unresolved Git submodules are unsupported in v1 and block capture.

Candidate identity is `sha256:<digest>` of a canonical manifest. The manifest has schema version 1 and an entries array sorted by UTF-8 path bytes. Every entry records a repository-relative POSIX path, entry kind, mode, byte length, and SHA-256 of file bytes or UTF-8 symlink-target bytes. Entries describe the complete selected tree; absence records deletion relative to the baseline. Canonical manifest JSON is the UTF-8 result of `JSON.stringify` on an object constructed in this exact key order: `schema_version`, `entries`; each entry is constructed as `path`, `kind`, `mode`, `byte_length`, `sha256`. Modes are `100644` or `100755` for regular files and `120000` for symlinks. There is no insignificant whitespace or trailing newline. Paths must be valid Unicode, retain their original code points without Unicode normalization, and have no empty, `.` or `..` components; sorting compares their encoded UTF-8 bytes. Unsupported filenames block rather than undergo lossy conversion. Duplicate or non-normalized paths are rejected. The bundle separately stores the bytes needed to reconstruct that manifest.

The integration MUST verify the reconstructed bundle against the manifest before review, proof, repair, export, or recovery. A path without its content, a truncated hash, `HEAD`, or a branch name is insufficient. Hashes and authoritative artifact references MUST be computed by coordinator/tool code, never accepted merely because a model supplied them.

Each verification invocation MUST also record an environment identity: container image digest, architecture, relevant runtime/dependency versions, non-secret configuration, test-service fixture identities, and the commands actually executed. Secrets are never included in a fingerprint or ordinary report. Where a secret affects behavior, record a non-secret credential-role/version reference supplied by the operator. A materially changed verification environment creates a new verification epoch and requires fresh evidence.

## 9. Artifact storage and phase results

Atomic’s checkpoints are authoritative for execution progression. The integration artifact store is authoritative for the immutable bytes referenced by handoffs. A local `status.json` may exist as a rebuildable projection, not a second recovery engine.

The run directory MUST contain a launch manifest, source snapshots, exact contract snapshots, candidate manifests and bundles, accepted phase envelopes, Markdown reports, evidence, approvals, effect receipts, and final or blocked handoff. Reports and evidence MUST remain outside all candidate trees. Several requirement rows may refer to one evidence artifact or one report section. [S1]

Each artifact reference contains `uri`, `sha256`, `byte_length`, and `media_type`. The resolver MUST retrieve the content, verify its length and digest, and validate any fragment/section locator. Local `file:` references are valid within the supported same-host run; export rewrites physical locations through a bundle manifest without changing logical identities. An expired or missing artifact prevents current acceptance and recovery.

The companion JSON Schema is the normative structural contract. Its named definitions cover launch inputs, candidate manifests, raw stage output, accepted phase envelopes, and final handoffs. JSON `null` denotes an explicitly unavailable field; omitted fields are allowed only where the schema permits them. A digest field named `sha256` contains 64 lowercase hexadecimal characters; `CandidateRef.id` prefixes that digest with `sha256:`. Full Git IDs have the repository’s supported 40- or 64-character object format. Authoritative artifact references and IDs are runtime-generated.

`ArtifactRef` has the fields above. `ContractRef` has `canonical_location`, `revision`, `sha256`, and `snapshot: ArtifactRef`. `CandidateRef` has `id`, `manifest: ArtifactRef`, `bundle: ArtifactRef`, `base_commit`, and nullable `matching_commit`. A raw `StageResult` contains `schema_version`, `phase`, identity `claims`, `report_markdown`, and the phase-specific `payload`. Claims include the source snapshot digest, contract triple, before/after candidate IDs, and comparison base. They are assertions to check, not authority to set runtime state.

An accepted planning envelope is constructed only after the approved contract is saved and reread. Before that point the raw planner result is a proposal artifact, not the current agreement. An unsuccessful planning result may be retained with a null contract reference.

Each accepted phase result MUST contain:

```ts
interface PhaseEnvelope {
  schema_version: 1;
  run_id: string;                 // Atomic run ID, runtime assigned
  invocation_id: string;          // Unique deterministic invocation ordinal
  phase: "plan" | "implement" | "review" | "prove" | "repair";
  verification_epoch: number;
  skill: { name: string; bundle_sha256: string };
  source_snapshot: ArtifactRef;
  contract: ContractRef | null;   // null only for an unsuccessful plan
  candidate_before: CandidateRef | null;
  candidate_after: CandidateRef | null;
  review_base: string | null;
  report: ArtifactRef;
  payload: PhasePayload;          // Discriminated by phase; section 10
  authorization_refs: ArtifactRef[];
  model_metadata: Record<string, JsonValue>;
}
```

The TypeBox implementation MUST make this a closed discriminated union, not a permissive object with every field optional. Plan envelopes have no candidate. Review and proof envelopes bind the same before/after candidate and cannot declare edits. Mutator envelopes identify both candidates. The model’s claimed identities are checked against runtime measurements; mismatches reject the output.

The model returns structured decision data and `report_markdown`. The coordinator validates and stores both, then creates the authoritative envelope. Markdown retains the normal Promise to Proof report shape. Normalized machine outcomes use underscores, for example `NOT_PROVEN`; the report retains `NOT PROVEN`. A deterministic report-format parser MUST check that the summary identity, outcome, coverage, and requirement verdicts agree with the structured fields. Routing itself MUST use validated structured data, never regular-expression or substring matching of prose.

Invalid schema, a missing report, contradictory representations, invented requirement IDs, or mismatched measured identities is `INVALID_PHASE_RESULT`. Preserve the raw response for diagnosis, redact where required, and stop. It is not evidence that implementation failed and MUST NOT automatically trigger a repair.

## 10. Typed skill payloads and evidence validation

All five payload schemas MUST reject unknown fields. A common `blockers` array carries structured reasons. Blocker categories are `CONTRACT`, `SOURCE`, `IDENTITY`, `AUTHORITY`, `ENVIRONMENT`, `DEPENDENCY`, and `CAPABILITY`; each entry includes a stable code, explanation, affected requirement IDs where known, and the smallest necessary next action.

### 10.1 Planning

`PlanPayload` contains `outcome: CONTRACT_PROPOSED | BLOCKED`, proposed contract bytes, revision, requirement index, unresolved evidence gaps, open product/design questions, exclusions, and change notes. `CONTRACT_PROPOSED` is an adapter outcome, not a new Promise to Proof acceptance verdict. Each index row contains `id`, source references, promise, boundaries, seam, independent oracle, planned evidence, and plan state. Contract revisions and stable requirement IDs follow the underlying protocol. [S1]

### 10.2 Implementation

`ImplementationPayload` contains `outcome: IMPLEMENTED | PARTIAL | BLOCKED`, selected requirement IDs, per-requirement implementation references and development checks, remaining gaps, supported review-finding dispositions when applicable, and proposed amendments. `IMPLEMENTED` requires all requested obligations and material development validation to be addressed. Already-sufficient code may qualify without a diff; the evidence must explain why.

A valid `PARTIAL` or `BLOCKED` result preserves the partial workspace and stops automatic progression. It does not authorize changing the agreement or starting an unbounded continuation.

### 10.3 Review

`ReviewPayload` contains `outcome: REVIEWED | CHANGES_NEEDED | BLOCKED`, full coverage IDs, inspection limits, findings, and proposed amendments. Each finding has a review-local ID, one of the contract-fidelity/scope/engineering axes, a requirement or binding-source reference, a precise location, inspected evidence, consequence, and proposed correction. Material findings are distinguished from optional advice.

`REVIEWED` requires complete requested coverage, no material change-required finding, and no decision-blocking unknown. Review MUST NOT assign proof verdicts. A review outcome cannot authorize a proof-gap repair.

### 10.4 Proof

`ProofPayload` contains `outcome: PROVEN | NOT_PROVEN`, a row for every contract requirement, contract reconciliation, observed identity stability, counterexamples, and unresolved gaps. Each row contains `requirement_id`, `verdict: proven | disproven | not_proven`, observation, independent oracle, and evidence references. [S2]

An evidence reference MUST identify the assertion or inspected invariant, actual observation/output, expected result, command and environment when execution was used, and a durable content reference with a locator. Static evidence must identify captured files and relevant locations. Merely naming a test, storing a command without its result, or citing an unrelated successful CI run does not satisfy the structural evidence requirement.

The validator MUST require exact set equality between the proof row IDs and contract row IDs; no duplicates, omissions, invented IDs, or empty set are permitted. `PROVEN` requires every row to be `proven`, complete required evidence references, no reconciliation discrepancy or unresolved gap, and unchanged captured identities. The skill evaluates whether evidence is substantively convincing and the oracle is independent. Schema validation alone MUST NOT be described as proving program correctness.

Each unresolved gap has one or more requirement IDs, a kind (`IMPLEMENTATION`, `EVIDENCE`, or a blocker category), a concrete explanation, and a proposed smallest complete repair where appropriate. Only `IMPLEMENTATION` and `EVIDENCE` gaps are eligible for automatic `repair-gaps`; the remaining kinds stop for resolution. [S2–S3]

### 10.5 Repair

`RepairPayload` contains `outcome: REPAIRED | NO_CHANGE | BLOCKED`, the matching failed proof reference, selected unresolved requirement IDs, addressed IDs, changed files/evidence, focused checks, and remaining gaps. Selected IDs MUST be a nonempty subset of the matching proof’s eligible unresolved IDs. The candidate and exact contract at repair admission MUST match that proof. [S3]

`REPAIRED` requires an actual scoped implementation or evidence change and successful focused checks. It does not imply that all requirements now pass. Even an evidence-only repair with unchanged source bytes requires a new full proof invocation. `NO_CHANGE` and `BLOCKED` stop automatic correction rather than repeat the same operation indefinitely.

## 11. Execution model and transitions

The workflow is dynamic execution within fixed protocol rules. Its top-level TypeScript determines branches from validated results. Each real invocation has a new deterministic ID; repeated verification or correction does not reopen a completed graph node. Phase names combine responsibility and invocation ordinal, such as `prove-0004` and `repair-0005`. Parallel review/proof IDs are allocated in a fixed order before dispatch. This implements repair cycles as an acyclic execution history. [S4–S5]

The integration maintains these logical states: `PREFLIGHT`, `PLAN`, `AWAITING_CONTRACT_APPROVAL`, `SAVE_CONTRACT`, `IMPLEMENT`, `CAPTURE`, `VERIFY`, `DECIDE`, `REVIEW_CORRECTION`, `PROOF_REPAIR`, `AWAITING_AMENDMENT_APPROVAL`, `FINALIZE`, and the five terminal outcomes. Atomic pause and awaiting-input states are lifecycle states orthogonal to this protocol state.

| State / result | Required action |
|---|---|
| Preflight succeeds | Invoke `plan-acceptance` with the exact source and any existing agreement. |
| Contract proposed, no outcome-defining unknown | Obtain exact-subject approval, save and reread, then implement. |
| Planning blocked or outcome unsettled | Preserve proposed material and stop `BLOCKED`. |
| Implementation `IMPLEMENTED` | Seal candidate and report; begin verification. |
| Implementation `PARTIAL` or `BLOCKED` | Preserve partial state and stop `BLOCKED`. |
| Review and proof both valid | Join both outcomes and evaluate the ordered reducer below. |
| Review correction authorized | Invoke `implement-contract` with supported finding IDs from the matching review. |
| Proof repair eligible and authorized | Invoke `repair-gaps` with the matching report, candidate, contract, and selected IDs. |
| Correction produces a usable candidate | Seal it, increment the verification epoch, and run full review and proof again. |
| Repair `NO_CHANGE` or `BLOCKED` | Preserve the report and stop `BLOCKED`. |
| Authorized amendment | Save a source-linked amendment; replan; approve/save/reread exact new contract; implement/reconcile under it; start a fresh verification epoch. |
| All completion conditions hold | Persist the final handoff, then emit `VERIFIED`. |

### 11.1 Ordered decision reducer

The following precedence is mandatory after review and proof settle:

1. A runtime failure, invalid output, candidate mutation, corrupt artifact, or policy violation prevents success. Preserve diagnostics and fail or block according to section 16.
2. A source/contract discrepancy or proposed material amendment takes the agreement-resolution path. No mutator may silently adopt it.
3. Missing authority, unavailable environment, unresolved prerequisite, or decision-blocking unknown stops automatic work. Supported findings remain visible in the handoff.
4. Valid `REVIEWED` plus valid `PROVEN` proceeds to finalization.
5. `NOT_PROVEN` containing only eligible, named implementation/evidence gaps routes to `repair-gaps`, provided the exact inputs still match and correction authority/budget remain.
6. Otherwise, `CHANGES_NEEDED` with valid `PROVEN` routes to an authorized implementation correction using the matching review findings.
7. All other combinations stop `BLOCKED` with their unresolved reasons.

When both review findings and eligible proof gaps exist, **proof repair takes precedence**. The review findings remain recorded, but cannot be silently added to the repair scope. After the repair, full review and proof run against the new candidate. The new review determines which concerns remain. An old review is not automatically reattached to changed code.

### 11.2 Parallel join and writer exclusion

In parallel mode, review and proof use distinct contexts, distinct reconstructed read-only candidate mounts, separate scratch/output directories, and isolated test services. Both receive the identical contract snapshot, candidate identity, source snapshot, comparison context, and verification epoch.

No correction may start when only one branch has completed. The coordinator MUST join both branches or cancel and fully stop the unfinished branch before any writer starts. Sequential mode does not weaken any identity or coverage check. Shared mutable test services are forbidden in parallel mode unless the execution profile proves isolation; otherwise the run must use sequential mode explicitly.

## 12. Currentness and the final gate

The comparison key for a current verification pair is:

```text
agreement = (canonical location, revision, exact contract digest, source snapshot)
verification = (agreement, candidate ID, comparison base, verification epoch)
```

Environment identities are also recorded and checked against the profile applicable to each stage. A proof and review may legitimately run in different declared verification environments; neither may silently switch its own environment or test target.

Any corrective invocation, material environment change, adopted source reconciliation, or authorized contract change increments the verification epoch. This prevents reusing an old successful pair after a repair merely because bytes later return to an earlier digest. Historical results remain immutable and inspectable; `STALE` is their relationship to the current target, not a rewrite of the original verdict.

Finalization MUST independently establish all of the following: the canonical agreement and source remain reconciled; every requirement is proven; review is complete and clean of material concerns; both reports use the current comparison key; evidence and candidate bytes remain retrievable; no writer or verification process is still active; no policy violation or pending material decision exists; and the final report has been saved and reread.

The finalizer MUST preserve the proof skill’s verdict, not manufacture a new `PROVEN` result. It emits integration outcome `VERIFIED` only after those mechanical consistency checks succeed. The final record includes `merge_readiness: NOT_ASSESSED`, the current candidate and reports, unresolved non-blocking observations, artifact location, and a UTC `verified_at` timestamp.

A completed result is a timestamped statement about a fixed candidate, not a permanent assertion about a moving branch. Subsequent application, commit creation, rebase, CI repair, or integration may require a new review/proof under Promise to Proof’s candidate rules. The workflow does not continue monitoring the work item after it terminates. [S1]

## 13. Authorization and role capabilities

Authorization MUST be recorded separately from model output. A grant binds an operator identity, exact subject digest, repository/work item, allowed operations and destinations, applicable before-state, issuance time, and any expiry or revocation conditions. A generic boolean such as `approved: true` emitted by an agent is not authority.

Interactive approval is collected through Atomic’s human-input interface and the integration’s operator-policy adapter. The adapter MUST distinguish direct operator decisions from model/tool-supplied answers and authenticate the approval record. Where the host cannot attest that distinction, use an operator-signed grant instead; otherwise stop `AUTHORIZATION_UNVERIFIABLE`. Headless execution requires a matching preauthorized grant and MUST NOT auto-answer a human gate. Source documents, issue comments, logs, and stage prompts never confer new authority.

The initial grant covers planning, managed-workspace creation, scoped local implementation/corrections, safe checks within the execution profile, and artifact storage. Canonical contract publication or source-link comments require a destination-specific grant. Contract-change approval MUST show the exact affected requirement IDs, old and proposed promises, changed boundaries/exclusions, and consequences; approval of an unspecified “revise the contract” action is insufficient.

| Role | Permitted | Prohibited |
|---|---|---|
| Planning | Read source/code; propose agreement and evidence plan | Product edits; publishing; acceptance claims |
| Implementation / review correction | Scoped writer-workspace edits; approved development checks | Contract edits; unrelated changes; commit/push/merge/deploy |
| Review / proof | Read captured inputs; run allowed checks with scratch/output writes | Candidate/contract edits; repairs; publication |
| Proof repair | Edit only what is needed for the selected matching gaps | Broadened scope; changed promises; acceptance claims |
| Coordinator | Persist approved bytes; seal snapshots; maintain artifacts; perform specifically authorized contract/source-link writes | Interpret approval into additional authority |

Atomic tool allowlists are necessary but not a security sandbox: permitting unrestricted shell execution would still permit writes. The profile MUST therefore route stage tools through role-bound implementations. The version-1 container profile mounts the captured candidate and agreement read-only for review/proof, exposes a writable managed workspace only to mutators, keeps evidence/scratch separate, and supplies no GitHub publishing credential, model-provider credential, Docker socket, host home directory, or privileged mount to candidate code.

Network access is denied by default. Necessary test services and dependency access must be declared and authorized in the profile; unavailable capabilities become explicit blockers. Verification MUST NOT install a formatter into the candidate, rewrite tests, or alter dependency/configuration files as setup. Mutating sensitivity experiments use separately identified disposable copies and cannot substitute their altered result for evidence about the fixed candidate.

The host/container isolation boundary is not claimed to defend against a compromised kernel or container runtime. Arbitrary production environments and live user data are excluded from the version-1 execution profile.

## 14. Skill invocation and structured-output adaptation

The adapter MUST resolve the approved skill by exact bundle content and preserve its reference directory. It MUST make the full skill and shared protocol available to the stage, rather than rely on the model spontaneously selecting a skill by description. Either explicit skill-command expansion or direct injection of the pinned skill content is allowed; the chosen approach must pass the same conformance test. Version 1 shall use direct pinned-content injection to avoid selection ambiguity.

Each new phase invocation uses `context: "fresh"`. A resumed unfinished phase may retain its own Atomic session. No implementer transcript, review deliberation, or proof deliberation is automatically shared with another phase; only the saved source, agreement, candidate, required reports, and explicit evidence handoffs are provided. Fresh context means a separate session, not statistical independence or infallibility.

The call pattern is the existing Atomic task API:

```ts
const task = await ctx.task(invocationName, {
  prompt: buildPinnedSkillPrompt(skillBundle, stageInputs),
  context: "fresh",
  schema: phaseResultSchema,
  tools: roleToolNames,
  customTools: roleToolImplementations,
});
// Validate task.structured, measure identities, store/reread artifacts,
// and construct the accepted PhaseEnvelope before deciding the next phase.
```

The helper names above are implementation components required by this specification, not existing Atomic functions. A schema-backed task’s `structured` field is the control-plane input; `text` alone is never the result API. The adapter MUST verify that the structured-output mechanism remains available under the configured tool policy. [S5]

The v1 adapter MUST expose role-scoped `p2p_read`, `p2p_list`, and `p2p_exec` tools. Mutators additionally receive `p2p_write`, `p2p_patch`, and `p2p_capture_candidate`. These are proposed integration tools, not Atomic builtins. Read/list operations resolve logical roots through the stage’s allowlist. Write/patch operations target only the writer root and require the expected prior content digest (or explicit file absence) before changing a file. Execution takes an argument array and an allowed working directory, runs inside the container, and records actual command, exit status, stdout/stderr references, and environment identity. Shells may execute only inside that same container boundary. Capture takes its workspace from trusted stage context, not a model-selected host path.

The effective stage tool set MUST contain only that role’s tools and Atomic’s schema-output mechanism. Inherited extension, subagent, workflow-launch, publishing, and unrestricted host-shell tools must not remain reachable through an alternate name. Returned command/read receipts are coordinator-generated evidence, not values the model can overwrite.

Each live tool admission checks the role grant and current relevant identities. The candidate-sealing tool computes and stores a reproducible snapshot outside the worktree; a mutator cannot invent an authoritative `candidate_after` value. A sealed candidate must still match the writer workspace when the mutator’s result is accepted.

## 15. Durability, idempotency, and resumption

Use `ctx.tool` for workflow-owned side effects, including contract persistence, source-link publication, candidate sealing, and accepted-envelope/final-report writes. Use deterministic invocation IDs and serializable arguments containing the relevant subject digests. Plain TypeScript is appropriate for pure validation and the transition reducer. [S7]

A completed checkpoint prevents replaying its completed callback; it does **not** guarantee exactly-once external effects when a process dies before the checkpoint is recorded. Every externally visible coordinator operation MUST therefore have a stable operation key, an intent record, a reconciliation procedure, and a confirmed readback receipt.

Local immutable writes use content-derived destinations, temporary files, atomic rename, and readback. Repeating an operation with identical bytes succeeds without another artifact; an existing destination with different bytes is a conflict. GitHub writes use a unique machine marker containing run, operation, and subject identities. After timeout or restart, the adapter searches all relevant destination records for that marker. One exact match is reused; multiple matches, mismatched contents, or unavailable reconciliation produce `SIDE_EFFECT_UNCERTAIN`. It MUST NOT blindly create another comment. Version 1 excludes concurrent independent publishers for one work item and does not claim atomic exactly-once semantics for the GitHub API.

Resume uses the same Atomic run and checkpoint history. Immutable inputs, workflow/skill/schema versions, and durable call order MUST remain compatible. Cached output is historical data, not evidence that the current canonical agreement or mutable workspace is unchanged. Live admission guards MUST revalidate the active execution frontier and its artifacts before new work or new tool effects; historical guards MUST NOT be replayed as new checks against a later workspace.

Supported recovery behavior is deliberately explicit:

| Interruption point | Required recovery |
|---|---|
| After a completed, accepted phase | Replay its checkpoint and accepted artifact references; continue from the next unfinished operation. |
| During a read-only review/proof | Resume that retained phase or rerun unfinished checks in new isolated scratch space against the same immutable inputs. No prior unrecorded observation is assumed. |
| After a coordinator write but before its checkpoint | Reconcile using the operation key and readback; reuse confirmed effects. |
| At an approval gate | Restore the bound request; reuse only a recorded, authenticated answer for the same exact subject. |
| During a mutating agent phase without a valid sealed-result handoff | Preserve workspace, transcript, diff, and partial snapshot; stop `INTERRUPTED_MUTATION`. Do not restart editing blindly or erase partial work. |
| After workflow/schema/skill incompatibility or artifact corruption | Stop with an actionable compatibility/integrity error; do not fabricate missing history. |

For an interrupted mutator, operator-approved adoption of an exact partial snapshot starts a **linked continuation run**. The continuation records the predecessor, original source and contract, partial candidate, remaining scope, and recovery grant; its first mutating phase is an explicitly authorized implementation continuation. It never labels the partial candidate implemented or proven. Correction/amendment counters carry forward, and limits cannot be reset by launching a continuation. This is separate from transparent same-run resume.

Automatic resume is permitted only at the safe checkpoints described above. The system MUST NOT claim durable recovery across hosts from a local file path. Cross-host continuation requires transferring and validating the complete artifact bundle and is outside the automatic version-1 resume promise.

## 16. Error taxonomy and stop semantics

Domain outcomes and execution failures MUST remain distinct. A model legitimately returning `NOT_PROVEN` is a successful execution of the proof phase with an unfavorable domain verdict. A provider outage or invalid JSON means no valid proof result was obtained.

| Class / examples | Integration outcome | Policy |
|---|---|---|
| Unsettled requirement, stale source, missing environment, missing authority, `PARTIAL`, `NO_CHANGE` | `BLOCKED` | Preserve state; identify required external resolution. |
| Corrupt artifact, invalid schema, dishonest/mismatched identity, prohibited mutation, protocol inconsistency | `FAILED` | Quarantine invalid output; no automatic acceptance or repair. |
| Exhausted correction/amendment limit or Atomic run budget | `BUDGET_EXHAUSTED` | Preserve all remaining findings; never raise a limit automatically. |
| Explicit operator cancellation | `CANCELLED` | Stop owned work; no automatic restart or takeover. |
| Provider/transport outage | `BLOCKED` after host handling is exhausted | Do not convert it into an implementation defect. |
| Uncertain publication / interrupted mutator | `BLOCKED` | Reconcile or obtain explicit recovery authority before further effects. |

Transient read-only operations and idempotent coordinator operations MAY use up to three total attempts, with a 1-second then 2-second delay. A mutating model phase is never automatically restarted by this retry policy. Atomic’s own model/provider retries must remain within the same role restrictions; a phase that has produced uncertain mutations takes the interrupted-mutation path. A failing behavioral assertion is evidence, not a transient error to retry until green.

Expected command failures used as proof data MUST return command exit status and output without being confused with workflow infrastructure failure. A `ctx.tool(..., {failureMode: "return"})` wrapper may represent such data, but the adapter must distinguish an assertion failure from a command that never ran. [S7]

Non-success terminal states MUST map to an appropriate non-success Atomic lifecycle using `ctx.exit(...)`; returning a normal “completed” graph with a concealed blocked payload is not conforming. Budget exhaustion uses Atomic’s native lifecycle where available and is also recorded in the integration handoff. If persistence itself fails, the UI must report the failure and any local emergency record without claiming that the final record is durable.

Pause/cancel propagates abort signals to subprocesses and services. New work is inadmissible once pause/cancellation begins. Late outputs from an abandoned execution are rejected by an execution-generation fence and cannot overwrite current results. Workspace ownership is released only after owned workers stop; partial files are not automatically deleted.

## 17. Budgets and bounded behavior

The automatic correction counter increments when either `implement-contract` is invoked for review findings or `repair-gaps` is invoked for proof gaps. No automatic corrective phase starts once the configured limit is consumed. Each successful correction is followed by an entirely new full verification pair, even when candidate bytes are unchanged.

The amendment counter increments when a post-approval agreement-change cycle is admitted. A contract change never resets correction counts. A continuation inherits cumulative counts. Atomic’s effective time, token, and cost budgets remain in force in addition to these deterministic bounds; the integration shall not silently disable them or invent an unlimited retry fallback.

When a limit is reached, the final handoff MUST show the current candidate, current agreement, latest review/proof, unresolved IDs and findings, consumed limits, and the exact operation that was not started. Approval to raise a limit is a separately authenticated operator action, not a model-generated “continue” decision.

## 18. User-visible output and retention

Status MUST show the source, Atomic run ID, logical phase, contract revision and digest, candidate ID, verification epoch, correction/amendment counts, pending approval, latest current review/proof outcomes, and the reason for any stop. Historical/stale reports must be visually distinguishable from current reports. Displayed hashes may be abbreviated, but copyable machine records must retain full values.

The final Markdown handoff MUST include the original promised outcome, canonical contract location and exact identity, candidate bundle and patch, fixed comparison base, review and proof references, evidence references, environment summaries, actual checks, limitations, and the explicit statement that CI/repository review/merge readiness are separate.

Artifacts and approval records are sensitive. Access should default to the owning operator, and DBOS credentials and signing material must never enter stage prompts or candidate mounts. Redaction is best-effort and is not a substitute for isolating secrets. The integration MUST NOT automatically delete a candidate, report, approval, or evidence artifact referenced by a retained run. Cleanup requires explicit operator action and a report of the recovery/historical references it would invalidate. [S7]

A bundle manifest MUST make the final candidate, agreement snapshots, reports, and evidence independently inspectable without reconstructing a chat session. Atomic checkpoint state is still required for same-run execution replay; an exported report bundle is not itself a replacement runtime.

## 19. Acceptance requirements and verification plan

The implementation is acceptable only when every requirement below has recorded passing evidence against one exact integration candidate. Test names are required fixture identifiers, not prescribed production filenames. Deterministic tests use a scripted skill runner and fake side-effect adapters; live integration tests use Atomic and a disposable fixture repository. Failure injection must be independent of model self-reporting.

| ID | Requirement and independent acceptance check |
|---|---|
| R1 | **Durable admission.** `durable-admission` runs against durable, memory, and missing-capability hosts. Only the durable host may admit a model or writer; failure is visible before edits. |
| R2 | **Pinned skill execution.** `pinned-skill-selection` installs colliding skill names and changed protocol references. The phase receives the approved bytes or blocks; it never silently selects the other skill. |
| R3 | **Unambiguous inputs.** `source-and-base-validation` rejects a foreign issue, missing repository, dirty unrelated source, invalid profile, and ambiguous base before mutation. |
| R4 | **Canonical contract handoff.** `save-readback-contract` verifies byte-for-byte approval, save, readback, one canonical location, and linked source. Simulated readback failure prevents implementation. |
| R5 | **Stable requirements.** `contract-index-validation` rejects duplicate/missing/retired-ID reuse and proof verdicts in plan state; approved material revisions preserve historical contracts. |
| R6 | **Recoverable candidate.** `snapshot-round-trip` covers changed/deleted/new files, executable modes, included ignored fixtures, and safe symlinks. Reconstruction is byte-identical; unsupported paths/gitlinks block. |
| R7 | **Independent verification stages.** `fresh-context-and-isolation` proves distinct sessions, identical target identities, isolated scratch/services, and absence of implementation transcripts. |
| R8 | **Read-only proof/review.** `verifier-mutation-denied` attempts candidate, test, contract, and source-checkout writes through every exposed tool, including shell. Writes are denied or the result is invalidated; no such run verifies. |
| R9 | **Schema and report consistency.** `invalid-phase-result` injects malformed output, missing structured data, false identity, conflicting Markdown outcome, and unknown fields. No downstream repair or success is admitted. |
| R10 | **Complete proof.** `proof-coverage-and-evidence` injects omitted/duplicate/invented rows, empty coverage, missing artifacts, nonexistent locators, and commands without results. Every invalid `PROVEN` claim is refused. |
| R11 | **Review correction route.** `review-to-implementation` gives `CHANGES_NEEDED` with a valid proof. Only implementation runs, using the matching finding IDs; both verification stages run again. |
| R12 | **Proof repair route.** `proof-to-repair` gives named eligible failed requirements. Only those IDs and the matching report/candidate reach `repair-gaps`; focused success never directly produces `VERIFIED`. |
| R13 | **Non-repairable failures.** `gap-classification` supplies missing credentials, ambiguous requirements, stale identities, and unavailable services. None is disguised as a code repair. |
| R14 | **Concurrent-result precedence.** `join-before-correction` controls review/proof completion order and delays one branch. No writer begins early; simultaneous eligible proof gaps and review findings take the prescribed proof-first route. |
| R15 | **Full invalidation.** `epoch-and-drift` changes candidate bytes, same-revision contract bytes, environment, and then reverts code to an earlier digest. Old reports remain historical; each required new epoch gets full review/proof. |
| R16 | **Amendment authority.** `amendment-gate` tests approval, rejection, changed proposal, and missing publication authority. Only approved source-linked amendments go through `plan-acceptance`; no other role edits agreement. |
| R17 | **Unforgeable permission.** `operator-grant-boundary` supplies approval-shaped model output, issue instructions, tampered/expired grants, and a tool-mediated gate answer. None acquires operator authority. |
| R18 | **Bounded convergence.** `correction-budget` and `amendment-budget` force continual failure. They stop at the exact configured boundary and retain unresolved work; continuations cannot reset counts. |
| R19 | **Checkpoint recovery.** `kill-after-checkpoint` terminates the Atomic process after an accepted phase, restarts it, and resumes the same ID. Completed work is not repeated and artifacts/identities remain unchanged. |
| R20 | **Uncertain-effect recovery.** `kill-after-effect-before-checkpoint` interrupts local and GitHub-fake writes at the critical window. Reconciliation reuses a confirmed effect or blocks; it never blindly duplicates publication. |
| R21 | **Interrupted mutation.** `kill-mid-implementation` verifies preservation of partial files and the explicit adoption/linked-continuation procedure. No partial work is lost or silently accepted. |
| R22 | **Cancellation fencing and ownership.** `cancel-late-writer` and `double-admission` prove that a late result cannot advance state, workers are stopped before lock release, and concurrent runs cannot share a writer. |
| R23 | **Final gate.** `final-gate-conjunction` tries each missing/stale/blocked input in turn. `VERIFIED` is possible only with a saved valid full pair and retrievable evidence; merge readiness remains unassessed. |
| R24 | **Host and profile compatibility.** The supported Node and Bun Atomic hosts execute the workflow with the container profile, typed output, custom tools, approvals, and durable resume. Unsupported hosts fail explicitly. |
| R25 | **Portable inspection.** `artifact-bundle-inspection` opens an exported final bundle without chat history and reconstructs its candidate, exact contract, reports, and evidence. Missing content is detected. |

In addition, at least two small real end-to-end fixture changes MUST be exercised. One must pass through the direct happy path. One must contain a deliberate behavioral defect detected by proof, receive a scoped repair, and pass fresh full verification. A third fixture must force an actionable review finding independently of the proof verdict. Fixture expectations and independent assertions are committed before the integration under test produces its reports.

The evidence package must identify the exact Atomic host build, integration candidate, skill bundle, test environment, commands, observations, and failures not yet resolved. A test plan, unit tests alone, or a convincing sample transcript is not a release verdict.

## 20. Implementation order and release gates

**Gate A — Host contract and isolation.** Implement the selected-backend capability, operator-authenticated grants, pinned skill loading, schema-backed custom-tool compatibility, and the read-only verification profile. Demonstrate R1, R2, R7, R8, R17, and the relevant R24 host checks before relying on the integration for unattended edits. Failure at this gate is an explicit compatibility blocker, not permission to weaken the specification.

**Gate B — Direct vertical path.** Implement source/contract resolution, save/readback, snapshots, the initial implementation, review/proof, and final gate. Deliver a real complete work item with R3–R10, R23, and R25 evidence. No automatic correction is required to demonstrate this intermediate increment, but it is not the final v1 release.

**Gate C — Controlled correction.** Add the ordered reducer, review corrections, eligible proof repairs, amendment approvals, epoch invalidation, and budget enforcement. Complete R11–R16 and R18.

**Gate D — Recovery and operational release.** Add critical-window effect reconciliation, safe resume, interrupted-mutation adoption, cancellation fencing, and exclusive ownership. Complete R19–R22 and repeat all conformance/end-to-end checks on the exact release candidate.

All gates are required for version 1. Repository changes MUST follow each repository’s existing contribution and issue-tracking requirements. This document does not authorize publishing issues, changing Atomic upstream, or merging an implementation.

## 21. Extension constraints

A later sliced-workflow release may compose child definitions using Atomic’s `ctx.workflow`. It MUST add qualified parent/child requirement mappings, prerequisite availability checks, isolated child workspaces, invalidation after parent amendments, an explicit integrated candidate, and full parent proof. A set of proven children MUST NOT be reduced into `PROVEN(parent)`. [S1, S5]

A later CI-repair release may invoke `fix-pr` only under a separate authorization profile that acknowledges its commit/push behavior. A changed candidate requires fresh applicable review and full proof. CI success must never stand in for the acceptance verdict.

A later merge integration must independently check current repository policy and the actual merge target candidate. Version 1’s `VERIFIED` record supplies evidence to that process but does not authorize it.

## 22. Design decisions and remaining implementation work

The following decisions are settled by this proposed specification: use Atomic rather than build a second runtime; implement direct delivery first; retain the existing skills as the substantive phase definitions; use structured phase data with readable reports; use recoverable snapshots without automatic commits; require a genuinely durable backend; enforce role isolation rather than rely only on prompts; make repair routing deterministic; authenticate consequential approvals; and fail conservatively at ambiguous recovery boundaries.

The main technical prerequisite is intentionally explicit: the checked Atomic public context needs the selected-backend capability in section 2.1 for a reliable durable-only admission rule. Operator-answer attestation and role-bound tool behavior must also be demonstrated through the conformance gate rather than assumed from the existence of a UI or a tool allowlist. These are concrete implementation tasks and release blockers, not undocumented assumptions that the current libraries already satisfy.

### 22.1 Mandatory semantic validators beyond JSON Schema

The schema does not express comparisons with other stored records or establish whether evidence is true. The implementation MUST additionally validate: contract-index equality with parsed Markdown; stable/retired requirement mappings; exact proof coverage; exact requested implementation coverage; review finding-ID uniqueness; result/report agreement; measured identity equality; proof-gap and repair-ID subset relations; approval subject/destination/scope/signature; candidate bundle round-trip; evidence retrieval and locator existence; full verification-key/epoch equality; and the final completion conjunction. Outcome-specific semantic checks reject `REVIEWED` with a material finding and `IMPLEMENTED` with an unresolved selected obligation. No cast from untrusted JSON may replace these checks.

Unknown schema versions and unsupported host capabilities fail closed. Schema evolution is an explicit integration release and compatibility decision; a retained run cannot adopt it just by renaming a stage.

No integration code has been implemented, executed, or accepted by this document. The specification’s acceptance table defines how that claim can later be established.
